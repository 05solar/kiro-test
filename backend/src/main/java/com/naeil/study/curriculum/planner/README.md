# curriculum/planner

시간 배분 알고리즘.

| 클래스 | 역할 |
| --- | --- |
| `CurriculumPlanner` | 계획 생성 |
| `CurriculumPolicy` | 우선순위와 압축 규칙 |
| `PlanningTopic` | 계획에 필요한 Topic 정보 (입력) |
| `PlannedStep` / `CurriculumPlan` | 계획 결과 (출력) |

## 서비스에서 분리한 이유

시간 배분은 이 프로젝트에서 가장 규칙이 많은 부분이다. 서비스에 넣으면 세션 검증,
DB 저장, 시간 계산이 한 메서드에 섞여 어느 규칙이 어디서 적용되는지 읽기 어려워진다.

분리해 두면 DB 없이 단위 테스트할 수 있고, 9단계 동적 재조정에서 같은 입력 형태를 쓸 수 있다.

## 입력과 출력이 엔티티가 아니다

`PlanningTopic` 은 `Topic` 엔티티에서 필요한 값만 복사한 record다.
Planner가 JPA에 묶이지 않아야 무작위 입력으로 수백 번 돌려볼 수 있다.

## 세 단계

```
1. 선택   우선순위 순으로, 최소 시간을 확보할 수 있는 주제만 담는다
2. 배분   남은 시간을 우선순위 순으로 나눠 권장 시간까지 늘린다
3. 정렬   원래 학습 순서로 되돌리고, 시간이 남으면 복습 단계를 붙인다
```

앞 주제가 안 들어간다고 멈추지 않는다. 뒤에 더 짧은 주제가 있으면 그건 들어갈 수 있다.
시간이 아주 부족할 때 큰 주제 하나 때문에 계획이 텅 비는 것을 막는다.

## 선택과 배분에 같은 우선순위를 쓴다

그래서 자신 없다고 표시한 주제는 같은 중요도의 다른 주제보다 시간이 덜 깎인다.
"취약 영역은 덜 축소한다"는 별도 규칙을 두지 않아도 그렇게 된다.

```
A HIGH 50분 (일반)     →  30분
B HIGH 50분 (취약)     →  40분
```

## 최종 순서는 topicOrder를 따른다

중요하다고 뒤 내용을 앞으로 끌어오면 선수 개념 없이 공부하게 된다.
중요도는 "무엇을 넣을지"에만 쓰고, "어떤 순서로 볼지"는 원래 순서를 지킨다.

## 스스로 검증한다

계획을 돌려주기 전에 제약을 확인한다.

```
합 <= 가용 시간 / 최소 시간 이상 / 권장 시간 이하 / 중복 없음 / 순서 연속
```

규칙으로 만들었으니 깨질 리 없다고 두지 않는다. 시간 총합을 넘기는 계획은
사용자에게 실행 불가능한 일정을 주는 것이고, 조용히 나가면 알아채기 어렵다.

## 정책 숫자는 휴리스틱이다

`CurriculumPolicy` 의 압축 비율(60% / 50% / 30%)은 MVP 기준값이지
학습 과학의 근거가 있는 값이 아니다. 실제 사용 결과를 보고 고칠 값이라 한 곳에 모아 두었다.
