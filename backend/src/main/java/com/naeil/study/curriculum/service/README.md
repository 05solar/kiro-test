# curriculum/service

| 클래스 | 역할 |
| --- | --- |
| `CurriculumService` | 계획 생성 / 조회 |
| `StudyStepService` | 단계 시작 / 완료, 실제 학습시간 기록 |

## 메서드

| 메서드 | 설명 |
| --- | --- |
| `create(sessionCode)` | 검증 → 가용 시간 계산 → Planner → 저장 |
| `find(sessionCode)` | 계획과 단계 조회 |

`CurriculumResult` 에 created 플래그를 담아 컨트롤러가 201/200을 구분하게 한다.

## 한 트랜잭션으로 처리한다

외부 호출이 없다. DB 조회, 계산, 저장뿐이라 분석 단계처럼 트랜잭션을 쪼갤 이유가 없다.

## 이미 계획이 있으면 다시 만들지 않는다

같은 요청을 두 번 보내도 결과가 같아야 하고, 사용자가 이미 본 계획이 새로고침 한 번에
바뀌면 안 된다. 그래서 존재 확인을 가장 먼저 한다.

세션이 IN_PROGRESS 로 넘어간 뒤에도 조회가 막히지 않는 것은 이 순서 덕분이다.
상태 검사를 먼저 하면 학습 중인 사용자가 자기 계획을 못 받는다.

## 시험까지 남은 시간 재확인

```
effectiveMinutes = min(세션의 남은 학습 시간, 지금부터 시험까지 남은 분)
```

시험 정보를 입력한 뒤 시간이 흘렀을 수 있다. 저장된 값이 300분이어도 시험까지
180분밖에 안 남았다면 300분짜리 계획은 실행할 수 없다.

더 짧아진 경우 세션의 값도 함께 낮춘다. 이후 단계들이 같은 기준을 보게 하기 위해서다.
늘리지는 않는다. 그 값은 학습 진행에 따라 줄어드는 값이다.

## 검증 순서

```
세션 조회 → 기존 계획 확인 → READY 상태 → Topic 존재 → 남은 시간
```

## StudyStepService

계획을 **만드는** 책임과 **수행하는** 책임을 나눈다.
한쪽은 세션당 한 번 일어나고 다른 쪽은 단계 수만큼 반복된다. 다루는 시간 값도 다르다.

| 메서드 | 설명 |
| --- | --- |
| `start(sessionCode, stepId)` | 검증 → 상태 전이 → 세션/계획 상태 갱신 |
| `complete(sessionCode, stepId)` | 실제 학습시간 기록 → 다음 단계 조회 → 계획 완료 판정 |

### 시작 검증 순서

```
세션 → 계획 → 단계 소유 → 완료 여부 → (진행 중이면 그대로 반환)
  → 시험 시각 → 다른 진행 중 단계 → 순서
```

"다른 진행 중 단계"를 순서보다 먼저 본다. STEP 1이 진행 중일 때 STEP 2를 시작하면
STEP 2는 첫 번째 `PENDING` 이라 순서 검사를 통과한다. 실제 원인은 동시 진행이므로
그 쪽을 먼저 알려주는 편이 맞다.

### 멱등하게 두는 두 경우

```
IN_PROGRESS → start     기존 상태 반환. startedAt 을 덮지 않는다
COMPLETED   → complete  기존 결과 반환. 다시 계산하지 않는다
```

409로 막으면 버튼을 두 번 누른 사용자가 오류 화면을 본다.
반대로 다시 계산하면 요청할 때마다 완료 시각과 학습시간이 늘어난다.

### 남은 시간을 차감하지 않는다

```
remainingStudyMinutes -= actualStudyMinutes   ← 하지 않는다
```

실제 학습시간에는 브라우저를 닫아 둔 시간까지 들어간다. 그대로 빼면 남은 학습 시간이
시험까지 남은 실제 시간과 어긋난다. 현재 시각과 `examAt` 을 함께 보고 다시 계산해야
하며, 그것은 9단계의 일이다. 여기서는 기록만 정확히 남긴다.

### 한 트랜잭션

단계 상태와 세션 / 계획 상태가 함께 바뀐다. 셋 다 성공하거나 셋 다 실패해야 한다.
