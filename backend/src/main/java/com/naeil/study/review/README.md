# review

세션 전체 정리. 공부를 마친 뒤 한 번에 훑어보는 화면이 쓴다.

| 하위 패키지 | 역할 |
| --- | --- |
| `service/` | `SessionReviewService` — 계획·요약·문제·답안을 한 번에 모은다 |
| `dto/` | `SessionReviewResponse` — 화면 세 갈래가 나눠 쓰는 응답 |
| `controller/` | `SessionReviewController` — `GET /api/sessions/{code}/review` |

API 명세: [`docs/api/review-api.md`](../../../../../../../docs/api/review-api.md)

STEP 하나의 풀이 내역(`GET /topics/{topicId}/quiz-review`)은 이 패키지가 아니라
[`quiz`](../quiz) 에 있다. 한 Topic 안의 일이라 퀴즈 도메인의 것이고,
여기는 세션 전체를 가로지르는 것만 맡는다.

## 왜 도메인을 따로 뒀나

이 화면은 세 도메인을 가로지른다.

```
curriculum  STEP 목록과 진행 상태
topic       STEP 별 요약과 핵심 포인트
quiz        문제와 내가 낸 답
```

어느 한쪽에 넣으면 그 도메인이 나머지 둘을 알게 된다. `curriculum` 이 퀴즈를 알 이유도,
`quiz` 가 학습 계획을 알 이유도 없다. 그래서 셋을 읽어 오는 일만 하는 자리를 따로 뒀다.

의존은 한 방향이다 — `review` 가 셋을 알고, 셋은 `review` 를 모른다.

## AI 를 부르지 않는다

정리 화면은 새로 만드는 것이 없다. 요약은 분석 단계에서 이미 만들어 `topics.summary` 에
넣어 둔 것이고, 문제와 답안도 채점 때 저장한 것이다. 모아서 줄 뿐이다.

정리를 열 때마다 요약을 새로 생성하면 두 가지가 무너진다.

- **볼 때마다 과금된다.** 시험 직전에 여러 번 열어 보는 화면이다.
- **같은 내용이 매번 달라진다.** 어제 본 정리와 오늘 본 정리가 다르면 "정리"가 아니다.

## 화면 세 갈래가 응답 하나를 나눠 쓴다

```
STEP 별 요약    steps[].summary, keyPoints
푼 문제 전체    steps[].quizzes 에서 answered 인 것
틀린 문제만     steps[].quizzes 에서 answered && !correct 인 것
```

틀린 문제만 보는 화면도 따로 부르지 않는다. 같은 자료를 세 번 받아 갈 이유가 없고,
탭을 옮길 때마다 기다리게 할 이유도 없다.

## 조심할 것

### 마지막 회차만 담는다

"새로운 퀴즈"를 만들면 같은 Topic 에 회차가 쌓인다. 전부 합치면 정리에 같은 범위의
문제가 두 벌 나오고, 문제 수도 실제로 푼 것보다 부풀어 보인다.

`quiz` 도메인의 `results` 와 같은 규칙이다.

### 완료 판정에서 SKIPPED 를 빼야 한다

시간이 모자라 잘라 낸 STEP 까지 끝내야 완료라면 영영 완료가 되지 않는다.
`PENDING` 이나 `IN_PROGRESS` 가 하나도 없으면 완료로 본다.

### 점수의 분모가 quiz 도메인과 다르다

| | 분모 |
| --- | --- |
| `quiz` 의 `results` | 전체 문제 수 — 학습 중 성취도 판단 |
| `review` | 실제로 푼 문제 수 — 끝난 뒤 되돌아보기 |

전자는 "아직 다 안 풀었다"를 점수로 드러내야 하고, 후자는 푼 것에 대한 평가다.
같아 보이는 두 수치를 하나로 합치지 않는다.

### N+1 을 피한다

STEP 마다 퀴즈를 물으면 STEP 수만큼 질의가 나간다. 이 화면은 STEP 전부를 한 번에
그리므로, 세션의 퀴즈와 답안을 한 번에 읽고 메모리에서 짝지운다.
