# API 문서 작성 절차

## API 하나를 문서화하는 순서

```
1. 엔드포인트    메서드 + 경로
2. 요청          path / query / body 파라미터와 제약
3. 부수 효과     조회인데 상태를 바꾸는가? (예: lastAccessedAt 갱신)
4. 성공 응답     실제 JSON 예시 + 필드 표
5. 오류 응답     상태 코드와 code 목록
6. 요청 예시별 결과 표
```

## 규칙

- 응답 예시는 **실제로 호출해서 받은 값**을 쓴다. 손으로 지어내지 않는다.
- 필드가 `null`일 수 있으면 표에 명시한다. 예시 JSON에도 `null`을 그대로 남긴다.
- 부수 효과가 있는 조회 API는 반드시 그 사실을 별도 항목으로 적는다.
- 아직 구현하지 않은 API는 `README.md`의 현황 표에만 두고, 상세 명세를 미리 쓰지 않는다.
  구현 전에 쓴 명세는 곧 거짓말이 된다.
- 명세와 구현이 다르면 문서를 고치기 전에 어느 쪽이 옳은지 먼저 판단한다.

## 갱신 시점

| 시점 | 할 일 |
| --- | --- |
| 새 API 구현 | 해당 도메인 문서에 절을 추가하고 README 현황 표를 갱신 |
| 응답 필드 추가 | 필드 표 + 예시 JSON 둘 다 수정 |
| 새 에러 추가 | error-codes.md 표에 한 줄 추가 |
| 정책 변경 | session-api.md 하단 정책 표 갱신 |

## 검증

문서를 고쳤으면 실제 호출로 확인한다.

```bash
curl -s -X POST http://localhost:8080/api/sessions
curl -s http://localhost:8080/api/sessions/{발급받은코드}
```

응답이 문서와 다르면 문서가 아니라 사실이 기준이다.
