System Architecture

내일까지 해야 하는데 — 시스템 도면

로그인이 없다. 8자리 세션 코드 하나가 접근 키이고, 그 아래에 강의자료 · Topic · 학습 계획 · 퀴즈가 매달린다. EC2 한 대 위에 올린 컨테이너 셋과 그 사이를 오가는 호출, 각 자리에 놓인 기술을 한 장으로 정리한다.

AWS EC2 · Amazon Linux 2023 Next.js 16 + React 19 Spring Boot 3.5 / JDK 21 PostgreSQL 16 Flyway V1–V5 Gemini · Anthropic
01

배치 — EC2 한 대, 컨테이너 셋, 열린 포트 하나

운영은 EC2 인스턴스 한 대다. 그 위에서 docker compose up -d --build 한 줄이 세 컨테이너를 띄운다. 인스턴스 밖에서 닿을 수 있는 것은 보안 그룹이 여는 80 뿐이고, 백엔드와 DB 는 expose 로만 열려 컴포즈 내부 네트워크에서만 보인다.

rewrites 대신 Route Handler 를 쓴 이유. next.config.ts 의 rewrites 는 destination 이 빌드 시점에 평가돼 이미지에 박힌다. 도커 빌드 때 백엔드 주소가 없으면 localhost:8080 이 그대로 굳어, EC2 에서 환경변수를 줘도 바뀌지 않는다. app/api/[...path]/route.ts 는 요청마다 BACKEND_URL 을 읽으므로 같은 이미지를 로컬 · 스테이징 · EC2 에 그대로 올린다.

03

요청 하나가 지나가는 길

화면 코드의 fetch("/api/…") 부터 SQL 까지, 모든 요청이 같은 계단을 밟는다. AI 가 필요한 요청만 아래로 한 번 더 내려간다.

04

도메인 파이프라인 — 코드에서 오답 요약까지

최상위 도메인은 User 가 아니라 StudySession 이다. 세션 코드가 발급되면 그 아래로 자료 → Topic → 계획 → 퀴즈 → 오답이 차례로 매달린다. 네 지점에서만 AI 를 부른다.

자료가 없어도 굴러간다. 업로드 없이 시험 범위만 적으면 source_type 이 일반지식 모드로 잡히고, 조각 분석 대신 범위 텍스트만으로 Topic 을 만든다(V2 마이그레이션). 파이프라인의 나머지 구간은 그대로다.
05

AI 경계 — 인터페이스 하나, 구현 넷

도메인 코드는 공급자를 모른다. 어떤 구현이 꽂힐지는 기동할 때 @Bean 이 설정값을 보고 한 번 정한다. 분석 · 퀴즈 · 챗봇 · 오답요약이 각각 같은 모양을 가진다.

응답 신뢰

모델 응답을 그대로 믿지 않는다

AiTopicResponseValidator · AiQuizResponseValidator 가 형식과 값을 검사한 뒤에야 엔티티가 된다. 정답 인덱스 범위, 선택지 개수, 빈 문자열이 여기서 걸린다.

재시도

연결 오류 · 429 · 5xx 에만

응답 형식이 어긋난 것은 재시도하지 않는다. 같은 프롬프트로 다시 불러도 같은 모양이 올 가능성이 크고, 그동안 사용자는 계속 기다린다.

프롬프트

도메인별 Prompts 클래스

AnalysisPrompts · QuizPrompts · ChatPrompts · WrongAnswerSummaryPrompts. 프롬프트가 코드 여기저기 흩어지지 않는다.

비용

보내는 양에 상한을 둔다

퀴즈 20,000자 · 오답요약 Topic 당 8,000자 · 챗봇 6,000자. 매 요청마다 문서 전체를 다시 보내지 않는다.

06

느린 작업을 화면에 보여주는 법

분석은 한 번의 동기 요청 안에서 조각 수만큼 모델을 부른다. 수십 초가 걸린다. 화면이 가짜 타이머를 돌리는 대신 지금 몇 번째 조각을 읽는 중인지 보여줄 수 있게, 진행도를 따로 뺐다.

07

데이터 — 테이블 10개, 뿌리는 하나

모든 행이 결국 study_sessions.id 에 매달린다. 세션이 만료되면 그 아래가 통째로 사라지고, EC2 볼륨의 원본 파일도 함께 지워진다.

스키마가 바뀌는 경로는 하나뿐이다

마이그레이션은 backend/src/main/resources/db/migration 에만 둔다. 백엔드가 기동하면서 Flyway 가 먼저 적용하고, 그다음 Hibernate 가 ddl-auto: validate 로 엔티티와 맞는지 검사한다. 두 겹인 이유 — 마이그레이션 파일을 빠뜨리면 Flyway 는 아무 불평 없이 성공한다. 어긋났다는 사실을 알려 주는 것은 뒤의 검증뿐이고, 그것도 EC2 가 아니라 내 컴퓨터에서 알려 준다.

  • V1 초기 스키마  ·  V2 일반지식 모드  ·  V3 챗봇  ·  V4 대화 순서  ·  V5 퀴즈 프롬프트 잔여 텍스트 정리
  • baseline-on-migrate — Flyway 도입 전에 손으로 만든 DB 도 V2 부터 이어 붙는다.
  • 운영 프로파일은 flyway.clean 을 아예 막아 둔다.
예전 방식이 실제로 죽였던 것. 컴포즈의 initdb 로 schema.sql 을 넣던 시절에는 빈 볼륨으로 처음 뜰 때만 동작했다. 데이터가 있는 DB 에는 아무 일도 일어나지 않아, 사람이 EC2 에 들어가 psql 로 먼저 적용해야 했고 그 순서를 한 번 틀리면 새 이미지가 기동 중 죽었다. 지금 docs/schema.sql 은 참고용이다.
08

EC2 위에서의 기동과 운영

배포는 인스턴스에 들어가 git pull 후 docker compose up -d --build 한 줄이다. 필요한 것은 저장소 루트의 .env 하나뿐이다.

인스턴스

t3.small 이상 · EBS 20GB

t3.micro 에서는 프론트 빌드가 메모리 부족으로 죽는다. 그런 경우 다른 곳에서 이미지를 만들어 ECR 에 올리고, EC2 는 받아 쓰기만 한다.

보안 그룹

인바운드 80 과 22 만

백엔드 8080 과 DB 5432 는 컴포즈 내부 네트워크에만 붙어 있어 그룹에 규칙을 더할 필요가 없다. 실제로 밖에서 안 열리는지 확인 목록에 넣어 뒀다.

순서

db → backend → frontend

각 단계가 condition: service_healthy 로 묶여 있다. DB 는 pg_isready, 백엔드는 /actuator/health. 없으면 첫 기동에서 연결 실패로 죽는다.

기동 유예

start_period 120초

첫 기동에는 마이그레이션이 함께 돈다. 작은 인스턴스에서는 JVM 기동만으로 30초를 넘긴다. 이 구간의 실패는 재시도로 세지 않는다.

시간대

Asia/Seoul 을 세 겹으로

app.timezone · 컨테이너 TZ · DB TZ. EC2 기본은 UTC 라, 두지 않으면 “남은 시간”이 9시간 부풀려진다.

데이터

볼륨 둘은 재배포에도 남는다

docker compose down 으로는 지워지지 않는다. 다만 down -v 는 db-data 와 uploads 를 지운다 — 사용자 데이터가 사라진다.

보존

매일 04:00 정리

마지막 접근 후 30일. 조회에 성공할 때마다 연장된다. 만료분은 200건씩 지우고, 볼륨의 파일도 함께 지운다.

비밀

키는 이미지에 넣지 않는다

인스턴스의 .env → 컴포즈 환경변수 → 프로세스. 로그와 예외 메시지에도 키를 넣지 않는다. 운영 프로파일은 .env import 자체를 끈다.

로그

운영은 root WARN

개발 기본값 DEBUG 를 그대로 올리면 로그 비용과 노이즈가 함께 커진다. 애플리케이션 패키지만 INFO.

배포 후 확인 순서

  • 세 컨테이너가 healthy 인가 — docker compose ps
  • 컨테이너 안의 시각이 KST 인가 — 이것부터 본다
  • 화면이 열리는가, /api/* 가 프록시되는가
  • 인스턴스 밖에서 8080 이 안 열리는가
