요청 하나가 지나가는 길
Controller
경로 매핑과 응답 변환만. 상태 전이 로직을 두지 않는다.
Service — @Transactional
검증 순서 · 유스케이스 조립. 여러 엔티티가 같이 바뀌면 한 트랜잭션 안에서 끝난다.
Entity
상태 전이 규칙 본체. 세터가 없고 start(now) 같은 의미 있는 메서드만 있다.
Repository
항상 소유 세션과 함께 조회한다. id 하나로 찾지 않는다.
AI Client
인터페이스로 감싼다. 도메인 코드는 Gemini인지 Anthropic인지 모른다.

AI 호출처럼 오래 걸리는 작업은 트랜잭션 밖으로 뺀다. 외부 응답을 기다리는 동안 DB 커넥션과 락을 잡고 있으면 안 되기 때문이다. 상태 기록은 짧은 트랜잭션으로 따로 쓴다.

시각은 주입받는다

엔티티 안에서 LocalDateTime.now() 를 부르지 않는다. Clock 빈을 주입해 서비스가 넘긴다. 시간에 의존하는 로직 전부가 테스트 가능해진다.

내부 id를 노출하지 않는다

외부는 8자리 코드로만 접근한다. UUID는 도메인 간 연관에만 쓴다. 없는 세션과 만료된 세션의 응답이 같다.

없으면 404, 남의 것도 404

다른 세션 자원에 403을 주면 “그건 존재한다”가 드러난다. 존재 여부 자체를 숨긴다.

01

자료를 읽는다

업로드와 텍스트 추출을 다른 요청으로 나눴다. 20MB PDF 열 개를 올리면서 동시에 파싱까지 하면 업로드 응답이 한참 돌아오지 않는다. 파일을 먼저 안전하게 받아 두고, 내용을 읽는 것은 그다음 요청에서 한다.

문서 상태 전이
UPLOADED → PARSING → PARSED
추출에 실패하면 → PARSE_FAILED

PARSE_FAILED 는 끝이 아니다. 다시 요청하면 재시도한다. 실패한 문서 하나 때문에 나머지 자료의 분석을 막지 않는다 — 분석 단계는 PARSED 문서만 골라 쓴다.

저장 경로에 원본 파일명을 쓰지 않는다

사용자가 올린 이름에는 ../ 도, 제어 문자도 들어올 수 있다. 서버가 만든 식별자로 저장하고, 원본 이름은 화면 표시용으로 DB에만 둔다.

저장소를 인터페이스로 감쌌다

지금은 로컬 디스크(LocalStorageService)다. S3로 바꿀 때 도메인 코드는 건드리지 않는다. 구현체 하나만 갈아 끼운다.

추출 텍스트에 @Lob 을 쓰지 않는다

PostgreSQL에서 @Lob String 은 본문 대신 OID(16411)를 저장한다. H2 테스트는 전부 통과했고 실제 DB에서만 드러났다. columnDefinition = "TEXT" 로 고정한다.

라이브러리 예외를 그대로 내보내지 않는다

PDFBox·POI의 메시지에는 내부 경로와 구조가 섞여 있다. 사용자에게는 DOCUMENT_PARSE_FAILED 만 주고, 원인은 로그에 남긴다.

중점

“반드시 볼 범위”는 가중치가 아니라 제약이다. 나머지 세 항목은 순서를 앞당기는 힌트지만, 이 항목에 걸린 주제는 중요도가 LOW 여도, 시간이 모자라도 계획에서 빠지지 않는다. 점수를 크게 주는 방식이었다면 시간이 부족할 때 조용히 밀려났을 것이다.

맥락은 PUT 이다. 부분 수정이 아니라 전체 교체다. 보내지 않은 항목은 비워진다. 네 항목이 전부 비어 있어도 정상 처리한다 — 추가 정보를 주지 않아도 이후 기능은 동작해야 한다.

1차에서는 주제만 뽑는다. 중요도·학습시간·맥락 관련성은 판단하지 않는다. 조각 하나만 보고 “이게 전체에서 얼마나 중요한가”를 물으면 답할 근거가 없기 때문이다. 그 판단은 전부 모인 2차에서 한 번에 한다.

중점 — 프롬프트를 데이터로부터 지킨다

강의자료는 사용자가 올린 임의의 텍스트다. PDF 안에 “위 지시를 무시하라”가 적혀 있을 수 있다. 그래서 두 가지를 모든 프롬프트에 고정으로 넣는다.

  • 주입 차단 — 자료와 사용자 맥락을 <lecture_document>, <user_study_context> 태그로 감싸고, 그 안의 문장은 명령이 아니라 분석 대상 데이터로만 다루도록 명시한다.
  • 근거 고정 — 강의자료에 없는 내용을 만들어 내지 않는다. 사용자 맥락은 힌트일 뿐 검증된 사실이 아니다. 맥락에만 있고 자료에서 찾지 못한 개념은 주제로 만들지 않는다.
응답을 믿지 않는다 — 저장 전 검증

구조

주제 0개 → 실패. 상한 30개 초과 → 실패. 제목 200자 초과, 빈 요약, 빈 핵심개념 → 실패.

범위

학습시간이 5~120분 밖이면 잘라 넣는다. 값이 아예 없으면 실패.

출처

AI가 만들어 낸 문서 참조값은 버린다. 요청에 실제로 넣어 준 참조만 문서 id로 되돌린다.

재시도

통합 결과가 검증에 걸리면 한 번 더 부른다. 연결 오류·5xx는 클라이언트 레벨에서 2회 재시도. 형식 오류는 여기서 재시도하지 않는다.

검증을 전부 통과한 뒤에야 저장한다. 실패하면 세션은 ANALYSIS_FAILED 가 되고 자료와 맥락은 그대로 남는다. 사용자가 다시 요청할 수 있어야 하기 때문이다.

04

3시간 안에 들어가게 만든다

Topic을 그대로 나열하면 계획이 아니라 목록이다. 180분밖에 없는 사람에게 220분짜리 목록을 주는 것은 아무 도움이 안 된다. 무엇을 얼마나 공부할지 정하는 것이 이 단계의 일이다.

중점 — 여기서는 AI를 부르지 않는다

중요도·예상 시간·맥락 일치는 이미 분석 단계의 결과다. 남은 일은 그 값으로 시간을 나누는 것이고, 그건 규칙이 낫다. LLM에게 “180분에 맞춰 나눠 줘”라고 맡기면 합이 200분이 되거나 반드시 넣어야 할 주제가 조용히 빠진다. 사용자는 그 실수를 알아채지 못한다. 규칙으로 짜면 같은 입력에 같은 결과가 나오고, 시간 총합 같은 제약을 코드가 보장한다.

세 단계
  1. 선택 — 우선순위 순으로, 각자의 최소 시간을 확보할 수 있는 주제만 담는다. 앞 주제가 안 들어가도 멈추지 않는다. 뒤의 짧은 주제는 들어갈 수 있다.
  2. 배분 — 남은 시간을 다시 우선순위 순으로 나눠 권장 시간까지 늘린다. 권장 시간보다 더 주지는 않는다.
  3. 정렬 — topicOrder 로 되돌린다. 중요하다고 뒤 내용을 앞으로 끌어오면 선수 개념 없이 공부하게 된다. 시간이 남으면 마지막에 복습 단계를 붙인다.

원래 순서

VERY_HIGH = 100, 교수 강조 = +30 같은 계수를 쓰지 않는다. 그런 숫자는 근거 없이 정해지고, 한 번 박히면 왜 그 값인지 아무도 설명하지 못한다. 무엇이 무엇보다 앞서는지만 정한다. 그리고 이 순서를 선택과 배분에 모두 쓴다 — 그래서 자신 없다고 표시한 주제는 같은 중요도의 다른 주제보다 시간이 덜 깎인다. 보정 규칙이 따로 없다.

압축 — 실제 배분 결과
프로세스와 스레드 50 / 50

중요도가 낮은 “파일 시스템”이 40분에서 12분까지 눌린다. 반면 중요도가 가장 낮은 “입출력”은 30분을 전부 지킨다 — 사용자가 반드시 보겠다고 한 범위이기 때문이다. 이것이 가중치와 제약의 차이다.

중요도별 압축 하한

10분짜리로 쪼갠 여러 개보다 제대로 본 몇 개가 낫다는 판단이다. 하한을 확보할 수 없는 주제는 계획에 넣지 않는다.

MVP 휴리스틱이지 학습 과학의 기준이 아니다. 고칠 값이라 CurriculumPolicy 한 곳에 모았다.

계획이 나가기 전 스스로 검사한다

규칙으로 만들었으니 깨질 리 없다고 두지 않는다. 하나라도 어긋나면 조용히 잘못된 계획을 내보내는 대신 실패한다.

  • 배정 합계가 가용 시간을 넘지 않음
  • 단계 순서가 1부터 연속
  • 각 단계가 최소 시간 이상, 권장 시간 이하
  • 같은 주제가 두 번 들어가지 않음

무작위 입력 60회 반복 테스트로 이 불변식을 확인한다.

시간 값을 세 개로 나눠 저장한다. originalEstimatedMinutes(원래 필요했던 시간, 이후 불변) / allocatedMinutes(이번에 배정한 시간) / actualStudyMinutes(실제로 쓴 시간). 하나로 합치면 “계획보다 12분 초과”를 판단할 수 없고, 뒤에 나올 동적 재조정의 근거가 사라진다.

05

계획이 현실과 어긋날 때

단계 진행
PENDING → IN_PROGRESS → COMPLETED
재조정에서 시간이 모자라면 → SKIPPED

순서를 지킨다

시작 가능한 단계는 PENDING 중 가장 앞선 하나뿐이다. 뒤부터 하면 시간이 모자랄 때 정작 중요한 단계가 남는다.

동시에 하나만

노트북과 휴대폰에서 각각 시작하면 같은 시간이 두 단계에 기록된다. 계획당 IN_PROGRESS 는 하나 이하다.

실제 시간은 서버가 잰다

화면 타이머 값을 받지 않는다. startedAt 과 완료 요청 시각으로 계산하고, 1초라도 지났으면 올림해 1분으로 센다.

중점 — 남은 시간을 빼지 않고 다시 계산한다

remaining -= actual 로 끝내면 안 된다. 실제 학습시간에는 사용자가 쉰 시간, 브라우저를 닫아 둔 시간까지 들어가 있다. 그대로 빼면 남은 학습 시간이 시험까지 남은 실제 시간과 어긋난다. 그래서 완료할 때마다 두 값 중 작은 쪽을 다시 구한다.

remaining = min(
   사용자 예산 - 완료 단계들의 실제 학습시간 합,
   지금부터 시험까지 남은 분
)
재조정 — 첫 단계가 예상보다 오래 걸렸다면
STEP 1 — 완료 실제 55 / 40
STEP 2 28 / 40
STEP 3 32 / 50
STEP 4 SKIPPED

최초 계획과 같은 우선순위, 같은 압축 하한을 쓴다. 규칙이 두 벌이면 계획과 재조정의 기준이 달라진다. 시간이 부족해 잘린 단계는 SKIPPED 가 되고 SkipReason.TIME_CONSTRAINT 를 남긴다.

순서가 중요하다

완료 기록 → 남은 시간 재계산 → 재배분 → 다음 단계 조회. 다음 단계를 재배분보다 먼저 찾으면, 방금 시간 부족으로 SKIPPED 된 단계를 “다음에 할 것”이라고 알려 주게 된다.

건드리지 않는 것

availableStudyMinutes(원본 예산), originalEstimatedMinutes, 그리고 이미 COMPLETED 된 단계의 모든 값. 계획 대비 실제를 비교하려면 기준값이 그대로 남아 있어야 한다.

06

공부한 것만 물어본다

퀴즈는 Topic 하나 단위로 만든다. 그리고 그 Topic의 학습 단계를 완료했을 때만 만들 수 있다. 안 배운 것을 물어보면 시험이지 복습이 아니다.

생성 전에 통과해야 하는 관문
세션이 존재하고 만료되지 않았다404 SESSION_NOT_FOUND
이 세션이 소유한 Topic이다404 TOPIC_NOT_FOUND
해당 Topic의 학습 단계를 완료했다409 TOPIC_STUDY_NOT_COMPLETED
출처 문서에서 근거 구간을 찾았다422 NO_QUIZ_SOURCE_CONTEXT
이미 만든 퀴즈가 없다 — 있으면 그대로 반환200 기존 반환
중점 — 문서 전체를 다시 보내지 않는다

“CPU 스케줄링” 문제를 만들자고 강의자료 전부를 AI에 보내면 비싸고, 관련 없는 내용에서 문제가 나온다. QuizContextExtractor 가 필요한 문단만 골라낸다.

  1. Topic의 제목과 핵심 개념을 키워드로 삼는다.
  2. Topic이 출처로 기록한 문서만 대상으로 한다. 세션의 모든 자료가 아니다.
  3. 문단 단위로 훑어 키워드가 있는 문단과 앞뒤 한 문단씩을 함께 담는다 — 정의가 앞 문단에, 예시가 뒤 문단에 있는 경우가 많다.
  4. 키워드가 하나도 안 걸리면 앞부분부터 잘라 넣는다. 근거가 아예 없는 것보다 낫다.
  5. 상한 20,000자에서 끊는다.

출처 문서가 전부 삭제된 경우에는 남은 파싱 문서로라도 시도한다. 그래도 비면 422 로 실패한다.

출제 규칙과 검증

프롬프트에 넣는 것

  • 보기는 정확히 4개, 정답은 하나만
  • 보기끼리 의미가 겹치지 않게
  • 핵심 개념을 문제마다 분산 — 같은 것만 반복해 묻지 않는다
  • 정답 위치를 한쪽으로 몰지 않게 분포
  • 해설은 추출 구간에서 확인 가능한 근거로
  • 난이도 EASY 1 · MEDIUM 2~3 · HARD 1 권장

저장 전 검증 — 하나라도 걸리면 전부 버린다

  • 문항 수가 3개 미만이거나 상한 초과
  • 보기가 4개가 아니거나 빈 보기가 있음
  • 보기 중 중복이 있음
  • correctIndex 가 0~3 밖이거나 없음
  • 문제·해설이 비었거나 2,000자 초과

전부 통과한 뒤 saveAllAndFlush 한 번으로 저장한다. 문제 일부만 남는 상태가 생기지 않는다.

맥락이 출제 방향을 바꾼다
교수님 강조 → 최소 한 문제
단, 자료에 근거가 있을 때만
기출 → 유사 유형 포함
기출을 그대로 복사하지 않는다
취약 영역 → 개념 구분·적용
단순 암기 문제로만 채우지 않는다
반드시 볼 범위 → 누락 금지
핵심 개념을 빠뜨리지 않는다
채점과 오답 요약
답안 제출 → 정오답 + 해설 즉시 반환 → 전 문항 완료 → 오답 요약 생성

정답 인덱스는 응답에 답안을 낸 뒤에만 들어간다. 퀴즈 조회 응답에는 문제와 보기만 있다. 모든 문항을 풀기 전에는 요약을 만들지 않는다(409 QUIZ_NOT_COMPLETED) — 절반만 보고 “당신의 약점은 이것”이라고 말할 수 없다. 틀린 문항이 없으면 AI를 부르지 않는다. 이미 만든 요약이 최신이면 그대로 돌려준다.

07

엔드포인트별 구현 초점

경로무엇을어디에 신경 썼는가
POST/sessions8자리 코드 발급혼동 문자를 뺀 32자 알파벳. 중복 시 최대 10회 재발급. 코드가 곧 접근 키라 서버만 만든다.
GET/sessions/{code}세션 조회조회할 때마다 보관 기한을 30일 연장. 없는 코드와 만료된 코드의 응답이 같다.
PUT/{code}/exam시험 정보min(입력 시간, 시험까지 남은 실제 시간). @Future 대신 주입한 Clock 으로 검증한다.
POST/{code}/documents자료 업로드개당 20MB · 10개 · 합계 100MB. 저장 경로에 원본 파일명을 쓰지 않는다.
DEL/{code}/documents/{id}자료 삭제DB 레코드와 실제 파일을 함께 지운다. 남의 세션 문서는 404.
POST/{code}/documents/parse텍스트 추출업로드와 분리. 문서별로 상태를 따로 기록해 하나가 실패해도 나머지는 진행한다.
PUT/{code}/study-context학습 맥락전체 교체. 네 항목 모두 선택 입력이고 전부 비어도 정상.
POST/{code}/analysisAI 분석조각 분석 → 통합 2패스. 프롬프트 주입 차단, 응답 검증 후 저장. 중복 실행은 409.
GET/{code}/topicsTopic 목록topicOrder 오름차순. 맥락 일치 여부를 boolean 네 개로 함께 준다.
POST/{code}/curriculum계획 생성이미 있으면 다시 만들지 않고 200으로 기존 반환. 새로 만든 경우만 201.
GET/{code}/curriculum계획 조회진행 상태·실제 학습시간·진행률까지 한 응답에. 그래서 “현재 단계 조회” API를 따로 두지 않았다.
POST/{code}/steps/{id}/start학습 시작순서·동시 진행·시험 시각 검증. 이미 진행 중이면 startedAt 을 덮지 않고 그대로 반환.
POST/{code}/steps/{id}/complete학습 완료실제 시간 기록 → 남은 시간 재계산 → 재배분 → 다음 단계. 재완료 시 값이 변하지 않는다.
POST/{code}/topics/{id}/quizzes퀴즈 생성학습 완료가 선행 조건. 출처 문서에서 관련 구간만 추출해 보낸다.
GET/{code}/topics/{id}/quizzes퀴즈 조회정답 인덱스를 내려보내지 않는다. 문제와 보기만.
POST/{code}/quizzes/{id}/answer답안 제출정오답과 해설을 즉시 반환. 재제출은 기존 결과 유지.
GET/{code}/topics/{id}/quiz-results채점 결과점수는 저장하지 않고 답안 기록에서 매번 센다.
POST/{code}/wrong-answer-summary오답 요약전 문항 완료가 선행 조건. 틀린 게 없으면 AI를 부르지 않는다.

멱등을 오류로 만들지 않는다

이미 진행 중인 단계에 start, 완료한 단계에 complete, 이미 있는 계획에 POST — 전부 기존 결과를 돌려준다. 버튼을 두 번 누른 사용자에게 오류 화면을 보여줄 이유가 없다.

201과 200을 구분한다

새로 만들었으면 201, 기존 것을 돌려줬으면 200. 만들지 않았는데 201을 주면 클라이언트가 생성 여부를 알 수 없다.

에러 코드는 한 곳에

약 40개를 ErrorCode enum에 모았다. 클라이언트는 code 문자열로 분기하고, message 는 그대로 화면에 띄울 수 있다.

08

어떻게 확인했는가

테스트 계층 — 56개 파일 · 850건
단위 — Mockito 11개 클래스 · 계획 알고리즘, 상태 전이, 검증기
슬라이스 — @WebMvcTest 12개 · 상태 코드와 JSON 형태
영속 — @DataJpaTest 6개 · 매핑, jsonb 왕복, 페치 조인
통합 — @SpringBootTest 13개 · HTTP로 전 구간

통합 테스트는 실제 포트를 열고 TestRestTemplate 으로 부른다. 세션 생성부터 퀴즈 채점까지 API만 써서 도는지 확인한다.

중점 — 테스트가 실제 AI를 부르지 않는다

FakeAiAnalysisClient, FakeAiQuizClient, FakeAiWrongAnswerSummaryClient 세 개를 두고 @TestConfiguration 으로 갈아 끼운다. 850건을 돌려도 과금이 0원이고, 응답을 마음대로 조작할 수 있어 “AI가 주제 0개를 돌려줬을 때” 같은 경로도 검증한다. Fake는 스프링 싱글턴이라 테스트 간 요청이 쌓인다 — @BeforeEach 에서 reset() 한다.

H2로는 안 잡히는 것이 있다

매 단계 실제 PostgreSQL에 붙여 통합 테스트를 한 번 더 돌리고 curl로 E2E를 확인한다. 이 절차가 @Lob String 이 본문 대신 OID를 저장하는 버그를 잡았다 — H2에서는 342건이 전부 통과했다.

불변식을 무작위로 때린다

계획 알고리즘은 @RepeatedTest(60) 으로 무작위 주제 조합을 넣어 “배정 합계가 가용 시간을 넘지 않는다”를 확인한다. 예제 몇 개로는 경계가 드러나지 않는다.

라이브 E2E는 환경변수로 잠근다

실제 Gemini에 진짜 강의자료를 넣는 테스트가 하나 있다. @EnabledIfEnvironmentVariable 로 GEMINI_API_KEY 와 자료 경로가 둘 다 있을 때만 돈다. 평소 빌드에서는 건너뛴다.

실패하면 다음 단계로 가지 않는다

단계마다 컴파일 → 단위 → 전체 → 실제 DB → clean build 순서로 확인하고, 통과하지 못하면 앞 단계를 다시 본다. 검증 실패와 조치를 PROCESS.md 에 남긴다.

관통하는 원칙

AI는 판단에만 쓴다

무엇이 중요한지, 어떤 문제를 낼지는 AI가 정한다. 시간을 몇 분씩 나눌지, 합이 맞는지, 반드시 볼 범위가 빠지지 않았는지는 코드가 보장한다. LLM이 잘하는 일과 규칙이 잘하는 일을 섞지 않는다.

모델의 응답을 믿지 않는다

구조·범위·출처를 전부 검사하고 통과한 것만 저장한다. 사용자 자료는 데이터일 뿐 지시가 아니라고 프롬프트에 명시한다. 조용히 이상한 결과를 내보내는 것보다 실패하는 편이 낫다.

기록은 나누고, 덮어쓰지 않는다

필요했던 시간 / 배정한 시간 / 실제 쓴 시간을 따로 둔다. 완료된 것은 다시 계산하지 않는다. 이 규율 덕분에 동적 재조정을 엔티티 구조를 바꾸지 않고 뒤에 얹을 수 있었다.

코드 하나가 전부다

회원이 없으니 8자리 코드가 유일한 접근 키다. 남의 자원은 존재 여부조차 알리지 않고, 내부 id를 밖으로 내보내지 않으며, 진행 상태는 전부 서버에 있어 어느 기기에서든 복구된다.
