01

전체 지도

이 서비스에는 회원이 없다. 서버가 발급한 8자리 코드가 유일한 접근 키이고, 모든 데이터가 그 아래 매달린다. 그래서 최상위 도메인은 User가 아니라 StudySession이다.

데이터가 매달리는 모양
8자리 코드 (7K2M9QXF)
      │
  StudySession ──┬── Document        올린 자료와 추출한 텍스트
                 ├── StudyContext    교수님 강조·기출·약점
                 ├── Topic ──┬── Quiz ── QuizResult
                 │           └── (StudyStep 이 참조)
                 ├── Curriculum ── StudyStep
                 ├── WrongAnswerSummary
                 └── ChatMessage     챗봇 대화

코드를 잃으면 되찾을 방법이 없다. 대신 코드만 있으면 어느 기기에서든 그대로 이어진다 — 진행 상태를 화면이 아니라 서버가 갖는 이유다.

흐름은 한 방향

자료 → 주제 → 계획 → 진행 → 퀴즈. 앞 단계가 끝나야 다음이 열린다. 건너뛰면 409로 막는다.

AI 는 네 곳에서만

분석 · 퀴즈 · 오답 요약 · 챗봇. 나머지는 전부 순수 계산이라 네트워크 없이도 돈다.

시간이 기준

"무엇을 공부할까"가 아니라 "남은 시간에 무엇까지 되나"로 계획을 짠다. 시간이 줄면 계획도 줄어든다.

02

파일 구조

계층이 아니라 도메인으로 먼저 나눈다. controller/, service/, repository/ 를 최상위에 두면 기능 하나를 고칠 때 멀리 떨어진 폴더 서너 개를 오간다. 여기서는 quiz/ 안에 퀴즈에 관한 것이 전부 있다.

com.naeil.study — 도메인 11개, 클래스 228개
패키지클래스맡은 일

studycontext7교수님 강조·기출·약점 (사용자가 아는 것)

curriculum39시간 배분, 단계 진행, 재조정
quiz33문제 생성(회차), 채점, 결과 집계
wronganswer22오답 기반 복습 요약

바깥 세계와 닿는 곳은 전부 인터페이스다. AI 공급자도, 근거를 고르는 방법도, 파일 저장소도 구현을 갈아 끼울 수 있다. 도메인 코드는 무엇이 붙었는지 모른다.

인터페이스를 둔 자리

  • AiAnalysisClient / AiQuizClient / AiChatClient — Gemini · Claude · Mock · Unavailable
  • StudyContextProvider — 지금은 키워드, 나중에 벡터 검색
  • StorageService — 지금은 로컬 디스크, 나중에 S3
  • DocumentParser — 확장자별 구현

문서도 코드 옆에

패키지마다 README.md, PROCESS.md, AGENT.md 를 둔다. 왜 그렇게 짰는지를 코드에서 멀리 떨어진 위키가 아니라 고칠 때 눈에 들어오는 자리에 남긴다.

03

어떤 기능이 있는가

1. 세션 — 회원 없는 접근

8자리 코드를 발급한다. 0/O/1/I 처럼 헷갈리는 글자를 뺀 32자 알파벳에서 뽑아 받아 적기 쉽게 했다. 마지막 접근 후 30일 보관하고, 조회할 때마다 연장된다.

2. 자료 업로드와 추출

PDF · DOCX · TXT. 업로드와 텍스트 추출을 나눴다 — 20MB 파일 여러 개를 받으면서 파싱까지 하면 응답이 한참 돌아오지 않는다. 저장 경로에 원본 파일명을 쓰지 않는다.

3. 학습 맥락

교수님이 강조한 것, 작년 기출, 자신 없는 부분. 자료만으로는 알 수 없는 것들이다. 사실의 출처가 아니라 우선순위 힌트로만 쓴다.

4. AI 분석 → 학습 주제

자료를 8000자 조각으로 나눠 후보를 뽑고, 한 번에 통합한다. 중요도와 예상 학습시간이 이때 정해진다. 자료가 없으면 과목명과 시험 범위만으로 만든다.

5. 학습 계획

남은 시간에 들어가는 만큼만 고른다. 중요도 순으로 담고, 넘치면 뒤에서 자른다. 시간이 남으면 마지막에 복습 단계를 붙인다.

6. 진행 기록과 재조정

단계를 시작·완료하면 실제 걸린 시간을 기록하고, 남은 시간을 다시 계산해 이후 단계의 배정을 조정한다. 예상보다 오래 걸리면 계획이 줄어든다.

7. 퀴즈 — 회차 개념

학습을 마친 주제만 출제한다. 채점은 서버가 한다(조회 응답에 정답이 없다). "새로운 퀴즈"는 기존 문제를 지우지 않고 다음 회차를 쌓는다.

8. 오답 요약 · 챗봇

틀린 문제만 모아 복습 요약을 만든다. 챗봇은 공부하다 막힌 것을 그 자리에서 묻는 기능으로, 무엇에 근거해 답했는지를 함께 돌려준다.

04

어떻게 고도화했는가

기능을 더할 때마다 이미 있던 것을 깨뜨리지 않는 방향을 골랐다. 아래 넷은 그 판단이 갈렸던 지점이다.

① 자료가 없어도 만든다
전 추출된 자료가 없으면 분석을 거절 → 서비스가 거기서 멈춘다
후 과목명 + 시험 범위로 일반 교과 지식에서 만든다

어려운 쪽은 만드는 게 아니라 감추지 않는 것이었다. 그렇게 만든 내용은 실제 수업 범위와 다를 수 있는데, 화면이 그 차이를 감추면 사용자는 자기 자료에서 나온 내용이라고 믿는다. 그래서 근거(sourceType)를 세션에 남기고 커리큘럼·퀴즈 화면에 항상 표시한다.

② 같은 범위로 새 문제

"다시 풀기"는 이미 낸 문제를 보는 것이고, 이쪽은 같은 범위에서 다른 문제를 만드는 것이다. 기존 문제와 답안 기록을 지우지 않고 회차를 올려 쌓는다. 이전 회차의 문제 문장을 AI 에 함께 보내 중복을 피한다.

겪은 것 UNIQUE(topic_id, quiz_order) 가 2회차 1번 문제를 막았다. (topic_id, round, quiz_order) 로 바꿨다 — 순서는 회차 안에서만 유일하다. 목으로는 안 잡히고 실제 DB 테스트에서만 드러난 문제다.
③ 학습 챗봇

답하는 것보다 무엇에 근거해 답했는지가 어려웠다. 값을 둘로 나눈다.

값단위뜻
grounded세션이 세션이 자료 기반인가
answeredFromMaterial질문이 답이 자료에서 나왔나

자료를 올린 세션이라도 질문이 자료 밖이면 두 번째는 false 다. 자료가 없는 세션에서는 모델이 규칙을 어기고 true 로 답해도 서버가 그대로 내보내지 않는다.

④ 마이그레이션을 배포 안으로
전 사람이 psql 로 먼저 적용 → 새 이미지 배포 (순서가 배포 밖에 있다)
후 기동하면서 Flyway 가 적용 → Hibernate 가 검증 (한 기동 안)
실제로 죽었다 Schema-validation: missing column [exam_scope] — 이미지를 먼저 올리자 컬럼 없이 기동해 죽었고, depends_on 때문에 프론트까지 뜨지 않았다. 순서를 지키게 만드는 대신 순서를 없앴다.
05

안정적으로 빌드하기 위한 구조

트랜잭션을 클래스에 걸지 않는다

AI 호출은 수십 초가 걸린다. 그동안 DB 커넥션을 잡고 있으면 커넥션 풀이 마른다. 상태 변경만 짧은 트랜잭션으로 떼어 낸다. 

AnalysisStateWriter.beginAnalysis()   짧게 (상태 → ANALYZING)
   ↓  AI 호출 — 트랜잭션 밖, 수십 초
AnalysisStateWriter.completeAnalysis() 짧게 (결과 저장)

스키마 검증을 두 겹으로

Flyway 는 쓰인 대로 적용할 뿐, 마이그레이션을 빠뜨렸는지는 모른다. 어긋났다고 알려 주는 것은 ddl-auto=validate 뿐이다. 로컬도 같은 설정이라 그 실패가 EC2 가 아니라 내 컴퓨터에서 먼저 난다.

실패를 미루는 구현체

API 키가 없다고 애플리케이션이 안 뜨면 AI 와 무관한 기능까지 막힌다. UnavailableAiClient 를 대신 등록해 기동은 시키고, 실제로 요청한 순간에만 실패시킨다.

기본값은 목(mock)

LLM_MODE=mock 이 기본이다. 화면을 한 번 확인할 때마다 과금되는 것보다 실수로 꺼져 있는 편이 낫다. 목 응답은 자기가 목이라고 본문에 적는다 — 실제 답변과 구분되지 않으면 원인을 한참 들여다보게 된다.

세션 삭제 순서를 한곳에

자식부터 부모 순으로 지운다. 리포지터리 여덟 곳에 흩어 두면 순서를 놓치고, 그날 이후 아무 세션도 지워지지 않는다. SessionPurgeRepository 한 곳에 모았다.

PostgreSQL 에서 @Lob 금지

@Lob String 은 OID 로 저장되어 값이 깨진다. 긴 문자열은 columnDefinition = "TEXT" 로 둔다. 4단계에서 실제로 겪고 규칙으로 굳혔다.

시각은 주입한 Clock 으로만

LocalDateTime.now() 를 직접 부르지 않는다. AWS 의 EC2·ECS 는 기본이 UTC 라 그대로 두면 남은 학습 시간이 9시간 부풀려진다. 에러 없이 틀린 답이 나오므로 더 위험하다. Clock 빈을 Asia/Seoul 로 고정하고 전부 주입받는다.

06

쓰인 기술과 그 원리

구조화 출력

자연어 응답을 정규식으로 뜯지 않는다. 응답 타입을 클래스로 넘기면 SDK 가 스키마를 만들고 검증된 객체로 돌려준다. 응답 필드는 Integer, Boolean 처럼 감싼 타입으로 둔다 — 값을 빠뜨렸을 때 0이나 false 로 조용히 채워지지 않게.

프롬프트 주입 방어

시스템 지시문과 데이터를 한 문자열로 이어붙이지 않는다. 자료·맥락·대화·질문을 각각 태그로 감싸고, 그 안은 전부 데이터라고 못박는다. "위 지시를 무시하라" 가 들어 있어도 명령으로 취급하지 않는다. 

SYSTEM RULES        규칙
<lecture_context>   자료      ← 데이터
<conversation>      지난 대화  ← 데이터
<question>          질문      ← 데이터

Grounding

자료에 없는 내용을 새로 만들지 않는다. 학습 맥락에 "B+ Tree" 가 있어도 자료에 없으면 주제로 만들지 않는다. AI 가 출처 문서 ID 를 지어내도 검증 단계에서 버린다 — 문서 ID 는 AI 가 만드는 값이 아니다.

컨텍스트 최소화

문서 전체를 매번 보내지 않는다. 키워드가 걸린 문단과 그 이웃만 골라 보낸다. 임베딩·벡터 검색은 쓰지 않는다 — 지금 규모에서 과하고, 바꿀 자리를 인터페이스로 열어 뒀다.

Flyway baseline

이력 표가 없는 기존 DB 를 만나면 V1 이 적용된 것으로 표시하고 그다음부터 이어 적용한다. 그래서 V2 이후는 멱등해야 한다 — 손으로 이미 적용해 둔 DB 에서는 다시 실행된다.

동시 실행 막기

같은 주제의 퀴즈 생성이 겹치면 그만큼 과금된다. 진행 중인 주제를 메모리에 표시해 두 번째 요청은 409 로 돌려보낸다. 화면에서도 버튼을 막지만, 눌린 뒤에 막는 것보다 안 눌리게 하는 편이 낫다.

07

어떻게 확인했는가

테스트 913건이 돌고, 그중 실제 AI 를 부르는 것은 하나도 없다. 과금되고, 응답이 매번 달라 테스트가 흔들리며, 네트워크가 없으면 실패하기 때문이다. AI 자리에는 전부 가짜 구현이 들어간다.

네 층으로 나눈 이유 — 각 층이 잡는 것이 다르다
단위 · Mockito — 12개 파일
JPA 슬라이스 · @DataJpaTest — 6개
웹 슬라이스 · @WebMvcTest — 12개
통합 · @SpringBootTest — 15개
단위분기와 계산. 시간 배분처럼 규칙이 많은 곳
JPA제약과 쿼리. 목으로는 절대 안 잡히는 것 — UNIQUE 위반이 여기서 드러났다
웹상태 코드와 응답 모양. 내부 사유가 새어 나가는지
통합실제 HTTP + DB 왕복. 긴 한글이 깨지지 않는지, 세션 경계가 새지 않는지

JVM 밖은 스크립트가 본다

테스트는 H2 로 돈다. PostgreSQL 문법인 마이그레이션 파일은 그대로 실행되지 않아 Flyway 를 꺼 두었다. 그 자리를 실제 컨테이너를 띄우는 스크립트가 메운다. 

migration-verify.sh  빈 DB / 구버전 / 최신 / 재기동  13건
gk-verify.sh         자료 없이 생성                  19건
chat-verify.sh       챗봇 근거 표시·세션 경계         19건

실제 AI 는 딱 한 번

무료 사용량을 아끼기 위해 5회만 실제로 불러 확인하고 기록했다. 같은 질문에 자료 있는 세션과 없는 세션이 다르게 답했고, 자료 있는 쪽은 자료의 용어를 그대로 썼다("순환 대기"가 아니라 "환형 대기") — Grounding 이 실제로 동작한다는 가장 분명한 증거였다.

테스트가 실제로 잡아낸 것
증상원인잡은 층
2회차 1번 문제가 저장되지 않음UNIQUE(topic_id, quiz_order)JPA 슬라이스
결과 화면에 정답이 undefined응답 DTO 를 추측으로 맞춤통합
답변이 질문 위에 표시 (확률 1/2)같은 시각 저장 → 정렬 기준이 무작위 UUID통합
계획 조회가 500지연 로딩 프록시를 트랜잭션 밖에서 초기화통합
기동 실패마이그레이션 미적용스크립트

위 셋은 단위 테스트로는 잡히지 않는다. 목은 개발자가 상상한 대로만 답하기 때문이다. 층을 나눈 값이 여기서 나온다.

엔드포인트별 구현 초점

메서드경로구현에서 중점을 둔 것
POST/api/sessions헷갈리는 글자를 뺀 코드. 중복 시 재시도
GET/api/sessions/{code}없는 코드와 만료된 코드에 같은 응답 — 존재를 알려주지 않는다
PUT/api/sessions/{code}/exam입력 시간과 실제 남은 시간 중 작은 쪽을 쓴다
POST/documents저장 경로에 원본 파일명을 쓰지 않는다
POST/documents/parse업로드와 분리. 일부 실패해도 나머지로 진행
POST/analysis자료가 없으면 과목명+범위로. 둘 다 없을 때만 거절
POST/curriculum이미 있으면 새로 만들지 않는다
POST/steps/{id}/complete실제 학습시간 기록 후 남은 단계 재배분
POST/topics/{id}/quizzes멱등 — 이미 있으면 AI 를 부르지 않는다
POST/quizzes/regenerate회차를 올려 쌓는다. 진행 중이면 409
POST/quizzes/{id}/answer채점은 서버가. 조회 응답에 정답이 없다
POST/chat지난 대화를 요청 본문으로 받지 않는다

다른 세션은 404

403 이 아니다. 403 은 "있지만 권한이 없다"를 알려 주는 셈이라, 코드를 넣어 보며 존재 여부를 알아낼 수 있다.

내부 사유는 로그에만

라이브러리 예외 메시지가 응답에 나가면 내부 구조가 드러난다. 사용자에게는 무엇을 하면 되는지만 말한다.

본문은 로그에 없다

질문·답변·자료 전문을 로그에 남기지 않는다. 사용자가 약점을 그대로 적는 자리라, 로그에 남으면 그게 곧 유출이다.
