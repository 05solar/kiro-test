# 프론트엔드 ↔ 백엔드 연동 테스트 기록

작성일 2026-08-28 · 대상 커밋: 프론트 연동 작업

프론트엔드(Next.js)를 백엔드(Spring Boot) API에 연결하면서 진행한 테스트의 과정과 결과.

관련 문서: [backend-anatomy.html](backend-anatomy.html) · [api/](api/) · [deployment.html](deployment.html)

---

## 1. 테스트 전략

### 왜 이렇게 나눴는가

AI를 부르는 경로는 호출할 때마다 과금된다. 그래서 **자동 테스트는 절대 AI를 부르지 않고**,
실제 AI 확인은 **딱 한 번만** 한다.

| 계층 | 대상 | 도구 | AI 호출 | 반복 |
| --- | --- | --- | --- | --- |
| 단위 | API 클라이언트, 어댑터 | Vitest (`fetch` 대체) | 없음 | 매번 |
| 타입 | 전체 | `tsc --noEmit` | 없음 | 매번 |
| 빌드 | 전체 | `next build` | 없음 | 매번 |
| 통합 | 전 구간 | 실제 서버 + 실제 Gemini | **있음** | **1회** |

### 무엇을 단위 테스트로 덮었는가

**API 클라이언트와 어댑터.** 이 둘이 백엔드와 화면 사이의 접합면이고,
여기가 어긋나면 예외가 나지 않고 **조용히 틀린 화면**이 나온다. 그게 가장 잡기 어렵다.

화면 컴포넌트는 단위 테스트를 붙이지 않았다. 렌더링 자체는 빌드와 실제 실행으로 확인했고,
로직은 전부 어댑터로 빼냈기 때문에 컴포넌트에 남은 것은 표시뿐이다.

## 2. 연동 구조

### CORS 대신 프록시

브라우저는 항상 같은 오리진(`/api/...`)을 부르고, 실제 전달은 Next 서버가 한다.

```
브라우저 ──▶ localhost:3000/api/sessions ──▶ localhost:8080/api/sessions
             (같은 오리진)                    (next.config.ts rewrite)
```

프론트(3000)와 백엔드(8080)는 포트가 달라 브라우저가 직접 부르면 preflight부터 막힌다.
백엔드에 CORS를 열 수도 있지만, 프록시 쪽이 낫다.

- 배포할 때 프론트와 백엔드를 같은 도메인에 두면 설정을 바꿀 필요가 없다
- 백엔드 주소가 브라우저 번들에 들어가지 않는다 (`BACKEND_URL`은 서버 전용 환경변수)

### 계획은 서버가 만든다

연동 전 프론트에는 `generateCurriculum()`이 있어 화면이 직접 시간을 배분했다.
백엔드에도 같은 일을 하는 계획기가 있다.

**둘 다 두면 화면에 보이는 남은 시간과 서버가 아는 값이 어긋난다.** 그때 어느 쪽이 맞는지
판단할 근거가 없다. 서버 하나로 정하고, 프론트의 계획 함수는 실제 데이터에 쓰지 않는다.

같은 이유로 진행 상태(완료한 단계)도 localStorage에서 서버로 옮겼다.
다른 기기에서 코드를 넣으면 그대로 이어지는 것이 이 서비스의 핵심이라, 화면이 따로 들고 있으면 안 된다.

### 화면에 남긴 것

`weakSteps`(다시 볼 개념)만 localStorage에 남겼다. 사용자가 직접 표시한 값이고
백엔드에 대응하는 개념이 없다.

## 3. 자동 테스트 결과

```bash
cd frontend
npm test              # Vitest
npx tsc --noEmit      # 타입
npx next build        # 빌드
```

| 항목 | 결과 |
| --- | --- |
| Vitest | **53 tests, 2 files, 0 failures** |
| `tsc --noEmit` | 오류 없음 |
| `next build` | 성공 (8개 라우트) |

### 무엇을 못박았는가

**어댑터 (`lib/api/adapt.ts`)**

- 중요도 4단계(`VERY_HIGH`~`LOW`)를 화면의 3단계로 줄이는 규칙
- 배정 시간과 원래 시간의 비율로 학습 모드를 정하는 규칙 (60% 이하 → 훑기)
- `SKIPPED` 단계를 목록에서 빼고 따로 넘기는 것 — 남은 할 일에 섞이면 사용자가 오해한다
- 감축률을 **잘린 단계까지 포함한** 원래 시간 기준으로 계산
- 0으로 나누지 않는 것 (단계 0개, 원래 시간 0분)
- 숫자 라우트(`/study/1`)와 서버 UUID를 잇는 표
- 시험 시각에 시간대 표기를 붙이지 않는 것 — `toISOString()`을 쓰면 UTC로 바뀌어 9시간 어긋난다

**클라이언트 (`lib/api/client.ts`)**

- 항상 같은 오리진 `/api`로 부르는 것
- FormData에 `Content-Type`을 붙이지 않는 것 — 경계 문자열은 브라우저가 만든다
- 백엔드 에러 코드·메시지를 그대로 담고, 세션 만료를 구분하는 것
- JSON이 아닌 오류 응답(프록시의 HTML 페이지)에도 터지지 않는 것
- 요청 취소(`AbortError`)를 오류로 바꾸지 않는 것
- 모르는 오류의 내부 메시지를 화면에 노출하지 않는 것

3. 큐와 원형 큐              30/30분

주제 합이 145분으로 남은 시간(178분)보다 적어 압축이 일어나지 않았고,
남은 33분이 복습 단계가 됐다.

```

3. [MEDIUM] 다음 중 스택 연산과 관련하여 오류가 발생하는 상황으로 옳은 것은?
4. [MEDIUM] 중위 표기식 'A+B*C'를 후위 표기식으로 올바르게 변환한 것은?
5. [HARD]   후위 표기식을 계산하는 과정에 대한 설명으로 옳은 것은?
```

올린 자료에 있는 내용(포화 조건 `top = N-1`, 언더플로, `ABC*+`)에서 나왔다.
난이도 분포도 프롬프트 지시(EASY 1 · MEDIUM 2~3 · HARD 1)와 맞는다.

**정답 필드가 응답에 없다.** 보기는 전부 4개다. 의도한 동작이다 —
정답을 내려보내면 개발자 도구로 다 보인다.

## 5. E2E에서 잡은 버그

### 채점 결과 응답 형태를 잘못 추측했다

프론트 타입을 이렇게 썼다.

```ts
interface AnsweredQuizResponse {
  quizId: string; order: number; question: string; options: string[];
  correctIndex: number; selectedIndex: number | null;
  correct: boolean | null; explanation: string;
}
```

실제 응답은 네 개뿐이었다.

```json
{ "quizId": "...", "selectedIndex": 0, "correct": false, "answeredAt": "..." }
```

결과 화면이 `item.options[item.correctIndex]`를 읽고 있어서 그대로 뒀으면
런타임에 `undefined`가 떴다. 타입만 맞춰 놓고 실제 응답을 확인하지 않은 탓이다.

**조치**

1. 타입을 실제 응답에 맞춰 고쳤다
2. 결과 화면이 퀴즈 조회를 함께 불러 `quizId`로 문제 본문을 이어 붙이도록 바꿨다
3. **실제 응답을 그대로 담은 회귀 테스트를 추가했다** — 같은 추측을 다시 하지 않도록

E2E를 한 번만 돌리기로 한 상황에서, 그 한 번이 이 버그를 잡았다.

### 남은 제약 — 결과 화면에 정답을 보여줄 수 없다

정답 번호는 **답안을 제출한 그 순간의 응답**에만 있다.
채점 결과 조회에도, 퀴즈 조회에도 없다. 그래서 결과 화면을 새로고침하면
"정답은 B였습니다"를 다시 만들 수 없어, 지금은 내가 고른 답만 보여준다.

백엔드 `AnsweredQuizResponse`에 `correctIndex`와 `explanation`을 넣으면 해결된다.
연동 범위를 넘는 변경이라 이번에는 하지 않았다.

## 6. 알려진 제약

| 항목 | 내용 |
| --- | --- |
| **맵 노드 7칸 고정** | `lib/mapNodes.ts`의 좌표가 7단계로 하드코딩돼 있다. 서버가 8단계 이상을 주면 맵에 안 나온다(오른쪽 STEP 목록에는 나온다). 자료 하나면 보통 3~7개라 당장 문제는 아니다. |
| **결과 화면 정답 미표시** | 위 5절 참고. 백엔드 응답에 없다. |
| **개발 모드 이중 호출** | React가 effect를 두 번 실행한다. AI 호출은 `useRef` 가드로 한 번만 부르게 막았다. |
| **화면 컴포넌트 테스트 없음** | 로직을 어댑터로 뺐고, 렌더링은 빌드와 실행으로 확인했다. |

## 7. 재현 방법

### 자동 테스트 (AI 호출 없음, 무료)

```bash
cd frontend
npm test
npx tsc --noEmit
npx next build
```

### 실제 E2E (AI 호출, 과금)

```bash
# 1. 백엔드 (.env 에 GEMINI_API_KEY 필요)
cd backend && ./gradlew bootRun

# 2. 프론트
cd frontend && npm run dev

# 3. http://localhost:3000 에서 순서대로 진행
```

**AI를 부르는 화면은 5(분석)·7(퀴즈)·8(오답 요약)이다.** 누를 때마다 과금된다.
같은 세션에서 다시 누르면 서버가 기존 결과를 돌려주므로 중복 과금되지 않는다.

# 부록 — 새로운 퀴즈 생성 (2026-08-28)

같은 학습 범위로 다른 문제를 다시 만드는 기능. **실제 AI 를 한 번도 부르지 않고** 검증했다.

## mock 모드로 검증한 것

```bash
QUIZ_AI_MODE=mock docker compose up -d --build
```

기동 로그에 경고가 남는다.

```
WARN  quiz.ai-mode=mock — 퀴즈를 AI 로 만들지 않고 목 데이터를 돌려준다.
```

| 확인 | 결과 |
| --- | --- |
| 1회차 생성 | 문항 5개 (목 데이터 1~5) |
| 새로운 퀴즈 | 문항 5개 (목 데이터 **6~10**) — 이전 문제를 받아 다르게 만든다 |
| 기존 데이터 | `round 1` 5문항 그대로 남음. 지우지 않는다 |
| 퀴즈 조회 | 마지막 회차(2회차)를 돌려준다 |
| 채점 결과 | 총 5문항 · 완료 true — 두 회차를 합치지 않는다 |

DB 상태:

```
 round | count | min | max
-------+-------+-----+-----
     1 |     5 |   1 |   5
     2 |     5 |   1 |   5
```

## 검증 중 잡은 버그 — 유일 제약

`(topic_id, quiz_order)` 로 잠겨 있어 **2회차의 1번 문제가 저장되지 않는다.**
1회차의 1번과 부딪힌다.

사용자가 "새로운 퀴즈 풀기"를 누른 순간에야 나타나는 종류라, 실제 DB 에 붙는
`@DataJpaTest` 로 못박았다. 목으로는 드러나지 않는다.

```
uk_quizzes_topic_id_quiz_order        (topic_id, quiz_order)
→ uk_quizzes_topic_id_round_quiz_order (topic_id, round, quiz_order)
```

`docs/schema.sql` 도 다시 뽑았다.

## 중복 호출 방지

- **프론트** — 요청 중 버튼 `disabled`, 문구를 "새 문제를 만드는 중…" 으로 바꾼다
- **백엔드** — 같은 Topic 의 생성이 진행 중이면 `409 QUIZ_GENERATION_IN_PROGRESS`
- **화면 진입만으로는 절대 부르지 않는다** — 사용자가 누를 때만 호출한다

mock 모드에서 연속 두 번 요청하면 둘 다 201 이 나온다. 목은 즉시 끝나 겹칠 틈이 없어서다.
실제 AI(수십 초)에서는 두 번째가 409 로 막힌다. 가드가 없다는 뜻이 아니라
목이 너무 빠르다는 뜻이다.

## 실제 Gemini 호출

이 기능으로는 **아직 하지 않았다.** mock 으로 흐름과 저장이 전부 확인됐고,
남은 것은 "AI 가 실제로 다른 문제를 만드는가" 하나다.
`QUIZ_AI_MODE=gemini` 로 한 번만 확인하면 된다.
