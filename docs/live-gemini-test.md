# 실제 Gemini 호출 검증 — 1회

목 모드로 확인한 것은 "경로가 이어진다"였다. 여기서는 **실제 AI 가 쓸 만한 결과를 내는지**를
확인한다. 무료 사용량을 아껴야 하므로 **한 번만** 돌렸고, 무엇에 몇 번 썼는지 아래에 적는다.

- 일시: 2026-08-28
- 환경: `docker compose` (db + backend + frontend), `PUBLIC_PORT=8090`
- 모드: `LLM_MODE=gemini`, 모델 `gemini-3.5-flash-lite`
- **실제 호출 5회.** 확인 후 곧바로 `LLM_MODE=mock` 으로 되돌렸다.

## 무엇에 몇 번 썼나

| # | 확인 대상 | 호출 | 소요 |
| --- | --- | --- | --- |
| 1 | 자료 없이 과목명 + 시험 범위로 주제 생성 | 분석 1회 | 7초 |
| 2 | 그 주제로 퀴즈 생성 | 퀴즈 1회 | 5초 |
| 3 | 같은 주제로 새 회차 퀴즈 — 실제로 다른 문제가 나오는가 | 퀴즈 1회 | 6초 |
| 4 | 자료 없는 세션에 챗봇 질문 | 챗봇 1회 | 2초 |
| 5 | 자료 있는 세션에 챗봇 질문 | 챗봇 1회 | 2초 |

**분석에 자료를 쓰지 않은 이유** — 자료를 올려 분석하면 조각 수만큼 호출이 늘어난다.
자료 기반 경로는 이미 라이브 E2E(`live-e2e-report.md`)에서 실제 강의자료로 확인했고,
이번에 새로 만든 것은 "자료가 없을 때"와 "챗봇"이라 거기에 예산을 썼다.

**5번에 새 세션을 만들지 않은 이유** — 자료 기반 챗봇을 확인하려면 자료가 추출된 세션이
필요한데, 그것을 새로 만들면 분석 호출이 한 번 더 든다. 이미 목 모드 검증에서 만들어 둔
세션(실제 텍스트가 추출되어 있고 `sourceType=USER_MATERIAL`)을 그대로 썼다.
챗봇이 보는 것은 그 세션의 **문서 텍스트**이므로, 주제가 목 데이터여도 근거 자체는 진짜다.

## 1. 자료 없이 주제 생성 — 분석 1회

입력은 이것뿐이다.

```
과목: 운영체제
시험 범위: 3장 프로세스와 스레드, 4장 CPU 스케줄링, 5장 교착상태
```

7초 만에 주제 9개가 나왔다.

```
프로세스의 개념과 상태
스레드와 멀티스레딩
프로세스 동기화와 IPC
CPU 스케줄링 개요와 기준
기본 CPU 스케줄링 알고리즘
라운드 로빈 및 다단계 큐 스케줄링
교착상태(Deadlock)의 이해와 조건
교착상태 처리 방법: 예방과 회피
교착상태 처리 방법: 탐지와 복구
```

**범위 세 개를 아홉 개로 쪼갰다.** 목 구현은 쉼표로 잘라 세 개를 만드는 것이 전부인데,
실제 AI 는 "4장 CPU 스케줄링"을 개요·기본 알고리즘·라운드로빈 세 단계로 나눴다.
벼락치기 계획으로 쓰려면 이 정도 입자여야 시간 배분이 의미가 있다.

첫 주제의 요약과 핵심 개념도 그럴듯하다.

```
요약: 운영체제에서 실행 중인 프로그램인 프로세스의 정의와 생성부터 종료까지의
      상태 변화를 이해한다.
핵심: 프로세스의 정의 / 프로세스 제어 블록(PCB) / 프로세스 상태 전이도
```

## 2 · 3. 퀴즈 생성과 새 회차 — 퀴즈 2회

같은 주제("프로세스의 개념과 상태")로 두 번 만들었다.

**1회차**

```
운영체제에서 실행 중인 프로그램을 의미하며, 디스크에 저장된 정적인 프로그램이
메모리에 적재되어 CPU를 할당받아 실행되는 동적인 단위를 무엇이라 하는가?
운영체제가 각 프로세스를 체계적으로 관리하기 위해 프로세스마다 유지하는 정보 블록으로,
프로세스의 상태, 프로그램 카운터(PC), CPU 레지스터 값 ... 은 무엇인가?
프로세스의 상태 전이 중, 프로세스가 CPU를 할당받아 명령어들을 실제로 실행하고 있는 상태는?
프로세스가 실행되던 중 입출력(I/O) 요청이나 이벤트 발생으로 CPU를 양도하고
해당 이벤트가 완료되기를 기다리는 상태는 무엇인가?
프로세스의 상태 전이 과정에 대한 설명으로 옳은 것은?
```

**2회차** (이전 문제 문장을 함께 보내 중복을 피하게 한다)

```
프로세스가 생성(New) 직후 운영체제로부터 승인을 받아, 메모리에 적재되어 CPU에 의해
실행되기를 기다리며 준비 큐(Ready Queue)에 대기하게 되는 상태를 무엇이라 하는가?
프로세스 제어 블록(PCB)에 대한 설명으로 가장 적절하지 않은 것은?
'준비 상태(Ready)'에서 '실행 상태(Running)'로의 전이가 일어나는 직접적인 계기는?
실행 상태에 있던 프로세스가 타이머 인터럽트 발생으로 CPU 할당 시간을 모두 소모했을 때,
이 프로세스의 상태 변화로 옳은 것은?
대기 상태(Waiting/Blocked)에 있던 프로세스가 기다리던 이벤트를 발생시킨 후 거치는 다음 상태는?
```

**겹치는 문제: 0개.**

같은 범위 안에 머무르면서(전부 프로세스 상태 전이와 PCB) 묻는 각도를 바꿨다.
1회차가 "실행 상태는?"을 물었다면 2회차는 "준비 상태는?", "타이머 인터럽트가 나면?"을 묻는다.
PCB 도 1회차는 정의를, 2회차는 "적절하지 않은 것"을 고르게 한다.

문장이 같은지만 비교하는 것으로는 "다른 문제"를 보장하지 못한다는 걱정이 있었는데,
실제로는 각도까지 달라졌다. 목 모드에서는 번호만 밀리므로 이건 실제 호출로만 확인할 수 있다.

## 4. 자료 없는 세션에 질문 — 챗봇 1회

```
질문: 교착상태가 생기는 네 가지 조건을 짧게 정리해줘
```

```
교착상태(Deadlock)가 발생하려면 네 가지 조건이 동시에 성립해야 하며,
하나라도 만족하지 않으면 발생하지 않는다.
- 상호 배제(Mutual Exclusion): 자원은 한 번에 하나의 프로세스만 사용할 수 있다.
- 점유와 대기(Hold and Wait): 이미 자원을 가진 상태에서 다른 프로세스가 가진 자원을
  추가로 기다린다.
- 비선점(No preemption): 다른 프로세스가 사용 중인 자원을 강제로 빼앗을 수 없다.
- 순환 대기(Circular Wait): 자원을 기다리는 프로세스 간의 관계가 원형으로 맞물려 있다.
```

```json
{"grounded": false, "answeredFromMaterial": false}
```

**"강의자료에 따르면" 같은 말을 하지 않았다.** 없는 자료를 있는 것처럼 말하지 말라는
프롬프트 규칙이 실제로 지켜졌다. 길이도 지시한 범위 안이고, 표나 코드블록을 쓰지 않았다.

## 5. 자료 있는 세션에 질문 — 챗봇 1회

같은 질문을, 강의자료가 추출되어 있는 세션에 던졌다. 그 자료에는 이 문장이 있다.

```
교착상태는 상호 배제, 점유와 대기, 비선점, 환형 대기 네 조건이 동시에 성립할 때 발생한다.
```

```
교착상태는 네 가지 조건이 동시에 성립할 때 발생한다.
- 상호 배제
- 점유와 대기
- 비선점
- 환형 대기
```

```json
{"grounded": true, "answeredFromMaterial": true}
```

**같은 질문인데 답이 다르다.** 4번은 각 조건에 설명을 붙였고, 5번은 자료에 적힌 네 단어를
그대로 옮겼다. 자료에 없는 설명을 덧붙이지 않은 것이다. 심지어 용어도 자료를 따라
"순환 대기"가 아니라 **"환형 대기"** 라고 답했다.

이것이 Grounding 이 실제로 동작한다는 가장 분명한 증거다. 두 답을 나란히 두면
어느 쪽이 자료를 보고 답한 것인지 눈으로 구분된다.

## 결론

| 확인 | 결과 |
| --- | --- |
| 자료 없이 과목명 + 범위만으로 쓸 만한 주제가 나오는가 | 그렇다. 범위 3개 → 주제 9개 |
| 그 주제로 퀴즈가 만들어지는가 | 그렇다 |
| 새 회차가 실제로 다른 문제인가 | 그렇다. 겹치는 문제 0개, 묻는 각도도 다름 |
| 자료 없는 챗봇이 없는 자료를 지어내는가 | 아니다 |
| 자료 있는 챗봇이 자료에 근거해 답하는가 | 그렇다. 자료의 용어("환형 대기")를 그대로 씀 |

응답 시간은 분석 7초, 퀴즈 5~6초, 챗봇 2초다. 챗봇 타임아웃을 45초로 잡은 것은
넉넉하다(분석·퀴즈는 180초).
