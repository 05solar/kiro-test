01

이번에 고친 것

시간대 — 가장 심각했다

시각을 LocalDateTime(시간대 없음)으로 저장하는데 현재 시각은 OS 기본 시간대로 잡고 있었다. 개발 PC는 KST라 맞았지만 AWS는 UTC다. 사용자가 넣은 시험 시각은 한국 시간이므로 남은 시간이 9시간 부풀려진다.

UTC 서버 — 고치기 전
33시간
실행할 수 없는 분량으로 계획이 잡힌다
→
고친 뒤
24시간
서버 시간대와 무관하게 같은 값

예외가 나지 않고 조용히 틀린 답을 낸다. 배포 후에 알아채기 가장 어려운 종류다. 그래서 OS 설정에 기대지 않고 app.timezone(기본 Asia/Seoul)으로 못박고, JVM 기본 시간대도 함께 맞췄다. 회귀를 막는 테스트도 넣었다. 

# 실제 확인 — 컨테이너를 UTC로 강제하고 띄웠다
docker run -e TZ=UTC ... naeil-backend

컨테이너 OS : Fri Aug 28 01:49:34 AM UTC 2026
애플리케이션: timezone fixed: Asia/Seoul (now=2026-08-28T10:49:25)

# 시험 3시간 뒤 · 예산 600분 → remainingStudyMinutes: 179  ← 정확
운영 프로파일 application-prod.yml
ddl-auto를 validate로 바꿨다. 운영에서 update는 컬럼 삭제나 타입 변경을 반영하지 않아 코드와 스키마가 조용히 어긋난다. SQL 로깅을 끄고, 로그 레벨을 INFO로 내리고, 오류 응답에서 스택트레이스를 뺐다. 프록시 뒤에서 원래 프로토콜을 인식하도록 forward-headers-strategy도 켰다.
헬스체크 /actuator/health
actuator를 넣고 health만 열었다. env·beans는 내부 구조를 노출한다. DB 상태를 함께 본다 — 200만 보고 살았다고 판단하면 DB가 죽어도 트래픽이 계속 들어온다.
Dockerfile 멀티 스테이지
JDK로 빌드하고 JRE에만 담는다. root로 돌리지 않는다. 힙은 MaxRAMPercentage로 컨테이너 메모리에 맞춘다. gradle.properties의 MS949는 한글 경로 대응용 Windows 전용이라 빌드 시 UTF-8로 덮어쓴다 — 그대로 두면 CloudWatch 로그의 한글이 깨진다.
만료 세션 정리 매일 04:00
“30일 후 삭제”라고 안내하면서 지우는 쪽이 없었다. 디스크와 DB가 무한정 늘어난다. 파일을 먼저 지우고 DB를 지운다 — 순서가 반대면 삭제에 실패한 파일의 위치를 잃는다. 한 번에 200건씩만 처리해 첫 실행이 DB를 오래 잠그지 않게 했다.
없는 주소가 500이었다 → 404 / 405
매핑되지 않은 경로가 전부 500 INTERNAL_ERROR로 나갔다. 인터넷에 붙는 순간부터 스캐너 요청이 끊임없이 들어오는데, 그게 다 오류로 잡히면 모니터링이 시끄러워져 정작 진짜 장애를 놓친다. 로그도 error에서 debug로 내렸다.
CORS 기본은 닫힘
프론트를 다른 도메인에 올릴 때만 CORS_ALLOWED_ORIGINS에 채운다. 비어 있으면 아무것도 등록하지 않는다. 기본값을 열어 두면 배포하는 사람이 눈치채지 못한 채 아무 도메인에서나 호출할 수 있게 된다.
스키마 마이그레이션 Flyway
백엔드가 뜨면서 db/migration의 밀린 스크립트를 적용한다. Hibernate 검증보다 먼저, 같은 기동 안에서 돈다 — 사람이 순서를 틀릴 단계가 없다. 이력 표가 없는 기존 DB는 V1로 baseline 되고 그다음부터 이어 적용된다.
02

남은 제약

업로드 파일이 로컬 디스크에 있다 인스턴스 1대
Fargate는 재시작하면 디스크가 사라진다. 2대로 늘리면 1번에 올린 파일을 2번이 못 찾아 STORED_FILE_NOT_FOUND가 난다.

지금 올리려면 — EC2 한 대 + EBS, 또는 ECS에 EFS를 마운트하고 STORAGE_ROOT_PATH를 그쪽으로 준다.
제대로 하려면 — StorageService 인터페이스에 S3 구현을 추가한다. 도메인 코드는 건드리지 않는다. 그러라고 감싸 둔 자리다.
AI 요청이 동기다 타임아웃 설정
POST /analysis는 요청 안에서 AI를 다 부르고 응답한다. 청크 N개 + 병합 1회라 실제 강의자료면 분 단위가 나온다. ALB 기본 유휴 타임아웃은 60초다. 클라이언트는 504를 받는데 백엔드는 계속 돌아 Topic을 저장하고, 사용자가 재요청하면 409 ANALYSIS_ALREADY_RUNNING으로 막힌다.

당장 — ALB 유휴 타임아웃을 300초로 올린다.
제대로 — 202를 먼저 주고 상태를 폴링하게 바꾼다. 퀴즈 생성과 오답 요약도 같은 구조다.
마이그레이션이 배포 안으로 들어왔다 해결
예전에는 docs/schema.sql과 docs/migrations/*.sql을 사람이 먼저 적용해야 했다. 두 단계의 순서가 배포 밖에 있어서, 새 이미지를 먼저 올리면 컬럼이 없는 채로 기동해 Schema-validation으로 죽었다 — 실제로 겪었다. 이제 Flyway가 같은 기동 안에서 적용하므로 그 순서가 뒤집힐 수 없다. 네 가지 DB 상태(빈 DB · 구버전 · 최신 · 재기동)를 scripts/migration-verify.sh로 확인한다.
세션 코드에 레이트리밋이 없다 WAF
32의 8제곱, 약 1.1조라 전수 대입은 비현실적이지만, 시도 자체에 비용이 없다. ALB 앞에 WAF 요청 제한을 두는 것이 가장 싸게 막는 방법이다.
키 관리

.env 파일은 로컬 개발용이다. spring.config.import에 optional:이 붙어 있어 파일이 없으면 건너뛰고 환경변수를 읽는다. 운영에서는 파일을 올리지 말고 ECS 태스크 정의의 secrets나 Secrets Manager로 GEMINI_API_KEY를 주입한다.

03

배포 절차

  1. RDS PostgreSQL을 만든다 — 빈 DB 로 둔다
    createdb naeil_study
    스키마를 넣지 않는다. 백엔드가 처음 뜨면서 Flyway 가 V1부터 차례로 만든다. 이미 테이블이 있는 DB 라면 V1이 적용된 것으로 표시하고 그다음부터 이어 적용한다.
  2. 이미지를 만들어 ECR에 올린다
    cd backend
docker build -t naeil-backend:1.0 .
docker tag naeil-backend:1.0 <account>.dkr.ecr.ap-northeast-2.amazonaws.com/naeil-backend:1.0
docker push <account>.dkr.ecr.ap-northeast-2.amazonaws.com/naeil-backend:1.0
    이미지 빌드는 테스트를 돌리지 않는다(-x test). 테스트는 CI에서 따로 돌린다. 리전은 서울(ap-northeast-2)을 쓴다 — 사용자가 국내이고 시간대도 KST다.
  3. 파일 저장 위치를 정한다
    EC2라면 EBS 경로를, ECS라면 EFS 마운트 지점을 STORAGE_ROOT_PATH로 준다. 이걸 정하지 않고 올리면 재배포할 때마다 사용자가 올린 강의자료가 사라진다. 컨테이너 안 /app/uploads가 기본값이며 볼륨으로 선언되어 있다.
  4. 환경변수를 넣고 태스크를 띄운다
    아래 “환경변수” 표 참고. GEMINI_API_KEY는 평문으로 넣지 않는다.
  5. ALB를 붙인다
    대상 그룹 헬스체크 경로 : /actuator/health
정상 임계값             : 2
간격                    : 30초
유휴 타임아웃           : 300초  ← 기본 60초로 두면 AI 요청이 끊긴다
    HTTPS는 ACM 인증서로 ALB에서 끊는다. 애플리케이션은 forward-headers-strategy로 원래 프로토콜을 인식한다.
  6. 확인한다
    아래 “배포 후 확인” 항목을 순서대로 실행한다.

05

배포 후 확인

# 1. 시간대 — 이것부터 본다
docker logs <container> | grep "timezone fixed"
→ application timezone fixed: Asia/Seoul

# 2. 프로파일
→ The following 1 profile is active: "prod"

# 3. 헬스체크
curl https://<domain>/actuator/health
→ {"status":"UP","groups":["liveness","readiness"]}

# 4. 관리 엔드포인트가 막혔는지
curl -o /dev/null -w "%{http_code}" https://<domain>/actuator/env
→ 404   (200이면 즉시 내린다)

# 5. 시간 계산 — 지금부터 3시간 뒤를 시험 시각으로
POST /api/sessions                → 8자리 코드
PUT  /api/sessions/{code}/exam    → availableStudyMinutes: 600
→ remainingStudyMinutes: 약 180   (720이 나오면 시간대가 안 잡힌 것)
5번이 핵심이다

나머지가 다 정상이어도 이 값이 틀리면 서비스가 실행 불가능한 계획을 내놓는다. 에러 없이 틀린 답이 나오므로 배포할 때마다 이 한 줄은 직접 확인한다.

재배포 전에

  • 엔티티를 고쳤다면 db/migration에 다음 번호의 마이그레이션을 넣었는가
  • 이미 나간 마이그레이션 파일을 고치지는 않았는가 — 체크섬이 어긋나면 기동 실패
  • 업로드 볼륨이 그대로 붙어 있는가

이런 증상이면

  • 기동 실패 — 스키마 미적용 또는 엔티티와 불일치
  • 분석이 504 — ALB 유휴 타임아웃
  • 파일을 못 찾음 — 볼륨 미마운트 또는 인스턴스 2대
  • 계획이 이상하게 김 — 시간대
요약

지금 올릴 수 있는 형태

EC2 한 대 + EBS + RDS + ALB(유휴 타임아웃 300초). 이 조합이면 지금 코드로 정상 동작한다. 도커로 실제 띄워 시간대·헬스체크·404 처리·시간 계산까지 확인했다.

여러 대로 늘리기 전에

S3 저장소 구현과 비동기 분석이 필요하다. 둘 다 인터페이스와 상태 필드가 이미 자리를 잡아 두어서, 도메인 로직을 바꾸지 않고 얹을 수 있다.
